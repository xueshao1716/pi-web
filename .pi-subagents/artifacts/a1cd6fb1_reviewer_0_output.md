## Review

### 总体判断

**视觉语言大约有 70% 像同一产品，基础框架统一，但复杂页面已经出现明显“各模块自己长”的漂移。**

统一感主要来自：

- 全局 `--pi-*` token、暗色表面、细边框、紧凑字号和统一圆角，见 `frontend/src/styles.css:29-145`。
- 非聊天页面普遍使用 `page-eyebrow`、`page-title`、`panel`、`card-hover`，例如 `Assets.tsx:64-68`、`Tasks.tsx:91-99`、`System.tsx:76-85`。
- 桌面端 rail、会话栏、内容画布的底色层级明确，见 `frontend/src/styles.css:217-219`、`frontend/src/AppLayout.tsx:272-306`。

问题不是缺少设计系统，而是**页面组织、状态表达和局部颜色没有完全服从这个系统**。基础组件像一个产品，页面信息架构有时像几个后台工具拼接在一起。

---

### Blocker

- **无阻塞级问题。** 当前问题以视觉一致性、信息层级和移动端导航认知负担为主，不是无法使用的结构性故障。

## 主要问题

### 1. High — 模型中心是当前最影响整体观感的页面

**位置：**

- `frontend/src/pages/ModelHub.tsx:108-218`
- `frontend/src/components/ModelChannels.tsx:37-86`

**问题：**

一个页面连续堆叠：

1. 页面标题；
2. 三张统计卡；
3. 服务商密钥管理；
4. Auto 路由说明；
5. 类型筛选；
6. 能力筛选；
7. 排序开关；
8. 搜索框；
9. 模型卡片网格；
10. Provider 用量表。

见 `ModelHub.tsx:123-218`。这些都是合理功能，但缺少明确的一级分区或渐进披露。用户进入页面后，统计、配置、选择模型和用量分析同时抢夺注意力。

模型卡内部也承载了图标、名称、免费标、provider/id、上下文、推理、视觉、备注、当前状态和切换按钮，见 `ModelHub.tsx:29-58`。大量卡片并列时会形成“徽章墙”，难以快速比较真正重要的字段。

**视觉影响：**

- 页面长、密、重复，容易显得像运维控制台而不是个人智能工作台。
- `ModelChannels` 和模型卡片都是同权重 `panel`，配置层与日常选择层缺乏视觉主次。
- 当前模型没有形成页面级焦点，只是在某张卡上加边框、光晕和绿点，见 `ModelHub.tsx:30-47`。

**建议：**

- 第一屏只保留“当前模型、Auto 状态、搜索/筛选、推荐模型”。
- “服务商通道”和“Provider 用量”改为折叠区或二级页；用量表已经折叠，通道管理也应同样处理。
- 模型卡默认只展示名称、来源、成本属性和核心能力；context、note 等进入详情。
- 将“切换使用”从每张卡片的大底部按钮收敛为选中态或单一主操作。

### 2. High — 移动端存在 TabBar、FAB、抽屉三套并行导航

**位置：**

- `frontend/src/AppLayout.tsx:208-260`
- `frontend/src/components/MobileFab.tsx:115-155`

**问题：**

移动端同时提供：

- 五项底部 TabBar；
- 可拖动 FAB；
- FAB 展开后的“全部功能”网格；
- 会话抽屉；
- 聊天页右面板覆盖层。

TabBar 把“设置”实际映射到 `models`，且仅当 `route === 'models'` 时显示活跃，见 `AppLayout.tsx:238-244`。从设置进入主题、系统等二级页面后，底栏没有对应的归属反馈。

FAB 又包含全部页面、会话和右栏，见 `MobileFab.tsx:115-141`，与底栏形成重复入口。这会让移动端不像经过简化的信息架构，更像把桌面功能全部塞进两个启动器。

**视觉影响：**

- FAB 长期悬浮，会遮挡资产网格、表单或列表末端内容。
- 底栏和 FAB 同时强调，主导航权重不清晰。
- 用户难以判断“资产/任务为什么在底栏，灵犀/应用/系统为什么在 FAB”。

**建议：**

- TabBar 保留 4–5 个真正一级入口。
- 第五项改成“更多”，打开统一菜单；取消独立悬浮 FAB。
- 设置下的模型、主题、系统形成明确二级导航，并保持“设置”活跃态。
- 会话继续作为对话模块内抽屉，不与全局应用菜单混在一起。

### 3. High — 桌面“右栏”实际是全屏覆盖，破坏三栏产品心智

**位置：**

- `frontend/src/AppLayout.tsx:308-325`
- `frontend/src/styles.css:217-219`

**问题：**

代码和注释都将其描述为“动态右栏”，但桌面实现是：

```tsx
fixed inset-x-0 bottom-0
```

即覆盖 rail、会话列表和聊天主体的全屏面板，见 `AppLayout.tsx:309-325`。这与前面建立的 `col-sidebar / col-canvas / col-right` 三栏视觉语言不一致。

工作空间、交付物、终端、活动和 TUI 又共享同一个顶部小型 Tab 条，功能跨度很大，却没有各自的页面标题和上下文。

**视觉影响：**

- 从聊天切到工作空间时，界面结构突然完全变化。
- “辅助上下文面板”变成了“另一个应用层”，空间关系消失。
- 顶部 40px 的五项文字 Tab 对全屏内容来说过弱，像临时调试面板。

**建议：**

- 宽屏恢复真正的可调宽度右栏，聊天上下文保持可见。
- 终端/TUI 若确实需要全屏，单独提供“展开”动作，而不是所有右栏内容一律全屏。
- 每个面板增加图标、标题和一句状态信息，避免只靠五个小文字按钮辨识。

### 4. Medium — 主题页明显脱离公共页面头部规范

**位置：**

- `frontend/src/pages/Themes.tsx:156-161`
- 对照 `frontend/src/pages/Assets.tsx:64-68`
- 对照 `frontend/src/pages/System.tsx:76-85`

**问题：**

多数页面采用：

- 英文 eyebrow；
- `.page-title`；
- 12px 辅助说明。

主题页却直接使用 `text-lg font-semibold` 和图标，见 `Themes.tsx:156-161`，没有公共 eyebrow/title 层级。这是非常具体的产品一致性断点。

主题页还混合了：

- 主题画廊；
- 即时聊天预览；
- 主色；
- 密度；
- 壁纸 URL/上传；
- 保存/重置/导出；
- Token 速览；
- shadow 展示。

见 `Themes.tsx:165-304`。面向普通用户的外观设置和面向设计开发者的 token inspector 混在同一页面。

**视觉影响：**

- 页面更像内部设计系统实验室。
- `step`、`shadow-sm/md/lg`、token 名称等技术信息削弱成品感。
- 页面比其他设置页更花、更长。

**建议：**

- 对齐公共页面头部。
- 默认只显示主题、主色、密度和壁纸。
- Token 速览、导出 CSS 收进“高级/开发者”折叠区。
- 实时预览可保留，但不必与主题卡片重复模拟聊天气泡。

### 5. Medium — 系统页优先展示“能力宣传”，实际操作被推到下方

**位置：**

- `frontend/src/pages/System.tsx:87-106`
- `frontend/src/pages/System.tsx:108-187`

**问题：**

进入系统页后首先看到大面积“系统能力”卡片网格，随后才是更新检测和网络配置。能力卡片偏产品介绍，而系统页通常更需要优先回答：

- 服务是否正常；
- 当前版本；
- 运行时间；
- 外网/局域网是否可达；
- 是否需要更新。

当前运行信息只浓缩在标题下方的一行 12px 文本中，见 `System.tsx:78-84`。

**视觉影响：**

- 高价值状态被弱化，宣传型内容占据第一屏。
- 所有能力卡使用相同 accent 图标底，扫视时区分度低。
- 整页由同尺寸 panel 组成，缺少“状态总览 → 操作 → 详情”的层级。

**建议：**

- 顶部改为 3–4 个状态摘要：服务、版本、运行时长、网络。
- “系统能力”降到页面末端并默认折叠。
- 更新与网络作为两个主要设置区。
- 网络地址、复制按钮和编辑域名应形成更明确的只读状态区/编辑区，而不是全部平铺。

### 6. Medium — 空状态实现不统一，产品语气和成熟度不一致

**位置：**

- 公共组件：`frontend/src/components/EmptyState.tsx`

- 正确使用：`frontend/src/pages/Apps.tsx:78-80`

- 纯文本实现：`frontend/src/pages/SessionDb.tsx:155`
- 纯文本实现：`frontend/src/components/ModelChannels.tsx:63-66`
- 纯文本实现：`frontend/src/components/ModelManager.tsx:49-53`

**问题：**

已有公共 `EmptyState`，但一些页面仍使用：

- 3xl emoji；
- 单行居中文字；
- 带 `<br>` 的临时提示；

### 7. Medium — 局部硬编码颜色削弱主题系统

**位置：**

- `frontend/src/components/Message.tsx:29`
- `frontend/src/components/Message.tsx:65-77`
- `frontend/src/components/Message.tsx:83`
- `frontend/src/components/Message.tsx:115`
- `frontend/src/components/Message.tsx:153`
- `frontend/src/components/Message.tsx:161-167`
- `frontend/src/pages/ModelHub.tsx:41-43`

**问题：**

聊天消息中大量直接使用：

- `purple-*`
- `sky-*`
- `gray-800`
- `red-500`
- `emerald-*`
- `bg-gradient-to-br`

例如推理内容固定紫色，系统提示固定天蓝色，用户头像固定红色，助理头像固定渐变。这些颜色在默认深色主题尚可，但切到 sepia、moss、mist 等主题后很可能显得像外来组件。

`styles.css` 已经提供 `--pi-info`、`--pi-success`、`--pi-danger`、`--pi-warning` 等语义 token，见 `styles.css:120-129`，却没有被这些组件完全利用。

**建议：**

- 推理、信息、成功、失败全部改用语义 token。
- 用户/助理身份色作为主题 token，而不是固定红色和蓝紫渐变。
- 保留必要的状态色，但避免 Tailwind 色板直接散落在业务组件。

### 8. Medium — 应用中心内部跨度过大，像五个后台模块共享一个壳

**位置：**

- `frontend/src/pages/Apps.tsx:10-18`
- `frontend/src/pages/Apps.tsx:161-182`

**问题：**

“经验沉淀台、技能库、提示词库、改进提案、记忆园丁”被放在同一级分段控件中。它们在用户目标、信息结构和操作强度上差异很大。

顶部文案还包含“专项生成”，但当前 Tab 列表没有专项生成，见 `Apps.tsx:166-168`，信息架构文案与实际入口不完全一致。

横向 Tab 在移动端使用 `overflow-x-auto`，虽然不会直接溢出，但隐藏的可横向滚动入口发现性弱。

**建议：**

- 应用中心先做应用卡片/入口页，再进入各工具。
- 或至少分成“知识资产”和“系统改进”两组。
- 当前活跃工具进入后应有工具级标题与操作说明，而不只是替换下面内容。
- 修正顶部说明，使其与实际 Tab 一致。

### 9. Note — 全站字体密度过度依赖 10–13px，小字层级过多

**证据：**

- 全局字号 token从 10px、11px、12px、13px密集递增，见 `frontend/src/styles.css:78-93`。
- ModelHub、Tasks、System、Themes 大量使用 `text-[10px]`、`text-[11px]`。
- Markdown 组件本身又强制 `text-[15px]`，见 `frontend/src/components/Markdown.tsx:51`，而全局 `.markdown-body` 定义为 13px，见 `frontend/src/styles.css` Markdown 区。

**判断：**

聊天正文更舒展，而设置页、任务页和模型页像高密度运维工具。差异可以是有意的，但当前 10/11/12/13 四档同时出现，视觉层级往往靠“更小、更灰”表达，容易产生疲劳。

**建议：**

- 主要正文最低 13px。
- 辅助说明以 12px 为主。
- 11px 只用于时间、ID、元数据。
- 10px 只用于紧凑 badge，避免用来承载操作或关键信息。

## 页面整治优先级（按收益排序）

1. **模型中心 `ModelHub.tsx`**
   - 收益最高：页面访问频繁、当前信息密度最大，也是“工具拼装感”最明显的位置。
   - 先做内容分层和渐进披露，不必先重画视觉。

2. **全局导航与右面板 `AppLayout.tsx` + `MobileFab.tsx`**
   - 统一移动端 Tab/FAB 信息架构；
   - 桌面恢复真正右栏或明确“全屏工具面板”的定位。
   - 这是影响所有页面的框架级收益。

3. **主题系统 `Themes.tsx`**
   - 对齐公共标题；
   - 用户设置和开发者 token 工具分层；
   - 能快速降低“内部实验页”观感。

4. **系统页 `System.tsx`**
   - 重排信息优先级；
   - 先状态、后操作、再能力说明。

5. **应用中心 `Apps.tsx`**
   - 从五个横向 Tab 改成有分组的工具入口；
   - 统一内部工具标题、空状态和主操作。

6. **会话库/任务中心**
   - 统一空状态；
   - 改善表格及任务操作在小屏下的呈现；
   - 降低 10–11px 元数据堆叠。

7. **聊天细节 `Message.tsx`**
   - 聊天主体结构相对成熟，不建议大改；
   - 主要清理硬编码色、渐变和不同主题下的适配。

8. **资产库 `Assets.tsx`**
   - 当前结构相对清楚，优先级最低；
   - 仅需补选中/批量操作、移动端灯箱 padding 等细节。

## 可保留的优点

### Correct — 1. 基础设计 token 完整且方向正确

`frontend/src/styles.css:29-145` 已涵盖：

- 背景层级；
- 文字层级；
- 语义颜色；
- 字体；
- 圆角；
- 阴影；
- 动效；
- 间距；
- z-index。

这说明不需要推翻视觉风格，重点是让页面和组件真正消费这些 token。

### Correct — 2. 多数页面头部和内容宽度已经形成稳定骨架

Assets、Tasks、ModelHub、Apps、System 普遍采用：

- `max-w-* mx-auto`
- `page-eyebrow`
- `page-title`
- 简短描述
- 面板式内容

例如 `Assets.tsx:63-68`、`Tasks.tsx:90-99`、`System.tsx:74-85`。这是当前最值得保留的产品统一感来源。

### Correct — 3. 资产库的信息组织最清楚

`frontend/src/pages/Assets.tsx:20-132` 的结构比较成熟：

- 搜索；
- 类型筛选；
- 自适应媒体网格；
- 统一卡片；
- 空状态；
- 交付物列表；
- 灯箱查看。

任务路径直观，主次清晰，是其他功能页可以参考的页面模板。

## 残余风险

- 本轮受工具预算限制，**未完成真实浏览器截图和桌面/手机视口逐页视觉走查**；上述结论来自 React、CSS 和运行结构的只读代码审计。
- 未读取或输出 `.token`，没有凭据泄露。
- 没有运行 Impeccable detector。
- 工作区本来已有未提交修改和未跟踪文件；本审计没有修改、暂存或删除任何文件。
- 浏览器层仍需重点补验：浅色 `mist` 主题、375px 移动端、低高度桌面窗口、壁纸开启后的文字对比度、全屏右面板的实际转场。
