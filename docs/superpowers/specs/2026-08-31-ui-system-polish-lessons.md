# pi-web UI 系统精修：可复用设计与验收笔记

> 来源：2026-08-31 `feat/ui-system-polish` 六批次实施。用于以后继续打磨 pi-web，而不是给本轮变更写流水账。

## 1. 高级感首先来自秩序，不是更多特效

深色科技工作台最容易滑向“发光卡片堆叠”：每块都强调，最后没有重点。本轮确定的顺序是：

1. 先稳定页面骨架、间距、字号、边框与表面层级；
2. 再让当前任务和主要操作成为视觉焦点；
3. 次要统计、开发者信息和能力清单默认折叠；
4. 动画只解释状态变化，不承担装饰任务。

复用原则：新页面先回答“用户进入后最先要做什么”，再决定首屏内容。不能把 API 返回的所有字段都平铺出来。

## 2. Token 是约束，不是配色参考

- 页面只能消费语义 Token，不得自行引入固定业务色或内联 hex。
- 状态色表达事实语义：成功、警告、错误、信息；不能因为“好看”给普通区域套状态色。
- 正文至少 13px，说明 12px，11px 仅元数据，10px 仅 badge。
- 统一焦点环、原生控件、圆角、阴影和缓动，比单独雕一张卡片更能提升整站一致性。

复用原则：发现某页需要专属颜色或专属控件样式时，优先判断是否缺少公共语义，而不是先写局部 class。

## 3. 公共组件要收口语义，不只减少重复代码

`PageHeader`、`SectionHeader`、`StatusTile`、`EmptyState` 的价值不是少写几行 JSX，而是固定：

- 页级标题、说明、操作区的优先级；
- 区块标题与辅助动作的关系；
- 状态摘要的标签和值层级；
- 空状态的 Lucide 图标、文案和下一步动作。

复用原则：公共组件 API 应限制错误表达。例如 EmptyState 只接收 Lucide 组件，不再允许 emoji；状态 Tile 不让页面自行定义任意字号阶梯。

## 4. 复杂页面应按“决策路径”组织

模型中心的有效结构是：

`当前模型 → 筛选 → 候选结果 → 通道与用量（折叠）`

主题页的有效结构是：

`主题画廊 → 实时预览与精调 → 开发者选项（折叠）`

系统页的有效结构是：

`真实状态摘要 → 更新/网络主任务 → 能力清单（折叠）`

复用原则：首屏服务当前决策，统计和实现细节下沉。折叠不是藏信息，而是保护用户注意力。

## 5. 响应式不是把桌面压窄

移动端应提供等价任务路径，而不是照搬桌面结构：

- 桌面 Apps 使用分组侧栏，移动端使用单一选择器；
- SessionDb 桌面使用表格，移动端使用信息等价的卡片；
- 桌面辅助工具是真右栏，移动端由“更多”菜单进入适合小屏的面板；
- 移动导航只保留最高频入口，低频设置进入“更多”。

复用原则：每个断点都检查信息是否等价、操作是否可达、重点是否仍清晰，而不是只检查 CSS 有没有换行。

## 6. 可访问性必须是行为契约

本轮验证的最低线：

- 移动触控目标至少 44px；
- dialog 有角色、标签、初始焦点、Tab 圈定、Esc 关闭和焦点回收；
- 同一时刻只存在一个有效 `aria-current`；
- 键盘焦点可见；
- reduced-motion 生效；
- 结构图标使用 Lucide，不用 emoji 代替。

真实浏览器曾测出 Apps 原生 select 只有 37px。静态 class 看起来“差不多”不算通过，最终要读取计算后几何尺寸。

## 7. 浏览器验收要区分产品缺陷和脚本误报

初版脚本出现 11 个失败，根因包括：

- 写入登录 token 后没有 reload；
- hash 路由后没有等待 lazy 页面和数据；
- selector 对 `data-slot` 和标题层级做了错误假设；
- 服务端主题偏好覆盖 localStorage；
- Chromium 将 44px 计算为 43.999969px。

改进方法：

1. 等待页面稳定标志（如当前路由 `h1`），不要只等固定毫秒；
2. 验收主题时临时拦截偏好 API，隔离真实用户状态；
3. 触控尺寸允许 0.5px 子像素误差；
4. 先用最小探针确认 DOM 与计算样式，再修改产品；
5. 报告脚本失败时必须写明它是“测试失败”还是“已确认产品缺陷”。

## 8. 视觉证据与能力边界要诚实

当前模型通道无法解析截图像素时，只能对 DOM、几何、交互、错误日志和结构契约下结论，不能假装完成肉眼审美评估。截图仍应保留，供后续可用视觉模型或人工复审。

复用原则：自动化证据能证明“不溢出、能操作、语义存在”，不能完全证明“好看”。两者不能互相冒充。

## 9. 构建与交付纪律

- 功能开发在隔离 worktree，保护主工作区未提交内容；
- 同一 worktree 只保留一个写入者；
- 先写失败契约，再实现，再跑全量验证；
- `frontend/dist` 只在最终发布构建时更新，开发分支验证后必须还原；
- 临时浏览器脚本只在运行时读取 token，报告不得写入凭据、请求头或敏感页面文本；
- 完成声明必须附测试、TypeScript、build、浏览器验收和 Git 状态证据。

## 后续 UI 迭代的检查顺序

1. 这个页面的第一任务是什么？
2. 首屏是否只有一个主要视觉焦点？
3. 是否复用公共 Header、状态、空态和 Token？
4. 次要信息能否下沉或折叠？
5. 桌面、平板、手机是否提供等价任务路径？
6. 键盘、Esc、焦点、ARIA、44px、reduced-motion 是否成立？
7. 结构契约、真实浏览器和人工/视觉审查是否分别完成？
8. 构建产物、敏感信息和主工作区脏改动是否受到保护？
